# Filesystem comparison research

Historical design snapshot. Its gap inventory describes the recorded revisions,
not current main. For current capabilities use [feature coverage](feature-coverage.md).

Research snapshot: 2026-11-04. This is a design and measurement specification, not an implementation or a claim of speed or complete parity. Primary comparators are **Rust `std::fs`, Go `os` filesystem APIs, and Goose `os`**. Honk is a secondary consumer/reference. Process execution, signals, environment management and pipes are outside this filesystem inventory; subprocess work belongs to goose-process.

Rust and Go offer portable filesystem interfaces with platform-dependent behavior, including Unix and Windows; neither means every operation works identically on every target. That is a **platform coverage gap**, not a security policy. Portability requirements must be decided explicitly, with unsupported capabilities reported rather than simulated silently. ## Semantics that must not disappear in a feature checklist

**Bounds and output ownership.** goose-fs caps path bytes at 4095, read/write/list payload at 1 MiB and lists at 4096 entries; list budget charges name bytes plus two bytes per entry. It clears read/list output on every error and replaces it on success; outputs own names. Allocator failure follows the Goose runtime, not `Status`. [F] Rust/Go whole-file conveniences have no corresponding fixed 1 MiB contract; Rust owns result buffers, Go may return partial data with errors, and Go directory reads explicitly support partial results. Goose read/list append into caller-owned builders; read rolls back appended bytes on `ferror`, ignores read `fclose` failure; list stages/sorts before append, so ordinary listing failure appends nothing. Buffer capacity can still grow. These are different observable contracts. [R][G][GDIR][SC]

**Path and symlink policy.** goose-fs rejects intermediate symlinks using `openat2(RESOLVE_NO_SYMLINKS)` or a descriptor walk on ENOSYS/EPERM; reads/list reject final symlinks, but remove-file deliberately unlinks a final link. This does not stop hard links, mounts or concurrent directory renames. Nonregular read targets are opened before type rejection and may invoke device-open callbacks. [F] Ordinary Rust/Go/Goose path APIs accept relative paths and generally follow links during traversal; lstat/readlink/unlink and exclusive creation have their own final-component semantics. `canonicalize`/`EvalSymlinks` intentionally resolve links and do not secure a later reopen. Lexical cleanup is not filesystem authorization. [R][RP][G][GST][GFP][SC]

Go `DirFS` is an interface adapter, **not** a confinement mechanism: symlinks may escape and relative roots depend on cwd. `Root` is a different security contract: relative operations cannot escape the tree, but in-tree relative symlinks are followed; mount boundaries, devices and `/proc` are not prohibited. Root itself is opened following links. Platform caveats include js TOCTOU exposure, plan9/js rename tracking and Unix metadata mutation races documented in the source. A strict no-symlink root would be useful but not behavior-identical to Go Root. [G][GR]

**Atomicity, overwrites, durability and partial success.** Rust/Go direct whole-file writes and Goose `write_file` truncate existing files; goose-fs create never overwrites but may leave partial newly created content. No one of these implies crash durability. [R][G][SC][F] Goose POSIX atomic write creates an O_EXCL sibling (up to eight random-tag attempts), initially mode 0666 before umask, copies existing target's 0777 bits using `stat/fchmod`, writes, syncs file, closes, renames, then best-effort syncs the parent. Parent-sync errors are ignored; therefore the public “flushed to disk” comment is stronger than its reported directory-durability result. Parent traversal can follow symlinks; mode inspection follows the target link while rename replaces its directory entry. Replacement can change inode/hard-link relationships. Windows uses exclusive creation, FlushFileBuffers and MoveFileEx replacement with retries; Unix and Windows contracts must be tested separately. [SC]

A new API should distinguish: accepted writes; atomic visibility of a complete new inode; checked file sync; checked parent-directory sync. A directory sync failure after rename means **publication may already have succeeded**. A binary failure code cannot imply “target unchanged.” Same-filesystem rename is required, and even native rename guarantees vary by platform/filesystem. [Linux rename][LR] and [fsync][LS] explain the Linux boundary; Go explicitly limits portability of atomic rename. [G]

**Errors.** goose-fs uses `InvalidInput/LimitExceeded/NotRegular/SystemError` plus errno only for SystemError, and does not embed paths/data in errors. [F] Rust uses `io::Result`, `ErrorKind` and optional raw OS error; partial I/O is represented by counts and errors. Go uses returned errors, `PathError`/`LinkError` (including paths), `errors.Is` compatibility and counts/EOF on handle I/O. [R][RIO][G][GE] Goose's booleans collapse absence, invalid path, permissions, resource exhaustion and I/O failure; existence helpers also collapse errors. [SC] Keep a stable portable error classification with native detail; don't treat raw errno as a portable backend contract.

**Safety choices versus gaps.** Absolute paths, default no-follow, private create modes, explicit work/memory limits, binary-safe output and redacted errors are defensible deliberate policies. They do not replace handles, metadata, streaming, links, timestamps, recursion or Windows support. Fixed whole-file bounds can coexist with large files through bounded chunks and 64-bit offsets. Relative access can be safe through a directory capability, without changing process cwd. Link inspection/creation and explicit link-following resolution should be separate operations from strict traversal. No claim of broad Rust/Go parity is justified while these gaps remain.

## Goose lifetimes: cleanup is available, but not automatic native ownership

The **pinned compiler has `defer`**. Block exit runs registered bodies in reverse order on normal fallthrough, break, continue, return and long-distance return. Loop-body defers run each iteration; bodies see variable values at exit, after return values are built. They cannot leave their scope, use long-distance-return machinery, or reference a named return result. [SL, defer section][SL]

This makes a small explicit handle API viable: successful open followed immediately by deferred close; successful lock followed by deferred unlock; successful temp allocation followed by deferred cleanup. Check close/sync explicitly when failure matters, invalidate/consume the resource, and use defer as fallback. Do not return a handle whose cleanup remains registered in the producing block. Do not capture a mutable descriptor variable and later reassign it unless its cleanup ownership is explicit. These are design implications, not existing goose-fs APIs.

Goose's memory lifetime checking does not turn a copied integer fd into a unique resource owner. The reference states that abort/assert/bounds failure/exit do not run defers; critically, a contained worker can end while native files/resources **stay open**. It also states there are no destructors in its long-distance-return mechanism. [SL sections 16, 20 and 22][SL] A native callback that calls abort across held resources is therefore not a safe cleanup boundary. Keep bounded one-shot operations self-cleaning in C; design handles with invalid states, explicit close, no double-close/use-after-close, and contained-worker cleanup strategy before claiming safety. Defer improves composition; it does not prove leak freedom or affine ownership.

**Streaming and portability limits.** Rust `Read`/`Write`/`Seek` and Go reader/writer/seeker interfaces permit fixed-size caller buffers; whole-file conveniences are not the right large-file baseline. Native filesystem byte/offset limits and supported seek targets still apply. Go file deadlines apply only where the underlying file supports them, and regular-file I/O must not be advertised as bounded-time. Native fd/raw-handle access and duplication are escape hatches, not ownership guarantees. [RIO][G][R] General filesystem watching, mmap and async I/O are not stable `std::fs`/`os` parity requirements in this inventory.

## Minimal coherent implementation stages

These are proposed milestones, ordered for a small reviewable interface. They cover the broader inventory without pretending the first milestone achieves parity. Every new behavior needs public-interface regression tests and the contributor-required format/check/test/GCC+Clang sanitizer checks and independent reviews. [FC] Names below are illustrative contracts, not code changes.

| Priority/stage | Small coherent surface | Testable acceptance criteria |
|---|---|---|
| 1. Contract and metadata | Keep six calls; add `stat`/no-follow entry metadata, error-preserving `exists/is_dir`, bytewise sorted-list helper. Define portable error categories and an explicit platform/capability table. | Missing vs EACCES distinguished; symlink/nonregular types covered; metadata output cleared on error; Unknown hint remains distinct; sorted output preserves CR/LF/non-UTF-8 names; existing adversarial traversal tests still pass. State Linux-only honestly until another backend passes. |
| 2. Owned handles and streaming | `open` with explicit read/write/create-new/truncate/append modes; close, read/write counts, seek, read_at/write_at, length/truncate, sync. Begin regular files only. | 6. Copy and convenience composition | Streaming single-file copy, selected-file copy, then tree-copy using root/walk; executable atomic install composes stream+mode+publication. A useful first expansion is stages 1–2, rather than adding many one-off wrappers. Metadata can serve predicates; handle primitives serve bounded whole-file helpers and copies; directory capabilities serve recursive algorithms; one publication core serves atomic bytes write and executable install. Goose defer supports all these compositions subject to the native cleanup limits above. Actual confinement and cross-platform guarantees need their own contracts and cannot be inferred from interface shape.

Go's `io/fs` is relevant architecture, not a mandate to clone its entire hierarchy: `FS.Open` returns a `File` with `Stat/Read/Close`; optional interfaces accelerate read-file, read-dir, stat, subtrees and readlink. Its names are UTF-8 slash-relative, no empty/dot/dotdot components except root `.`. That differs from arbitrary-byte native Unix names; keep native and virtual path domains distinct. `WalkDir` offers deterministic lexical order at a directory-memory cost. A Goose adapter should preserve errors, limits and names instead of silently accepting only the intersection. [GFS][GFW][GFR][G]

## Secondary Honk evidence and consumer requirements

Honk is not a substitute for the three primary targets. The following derives from the published native source, not private integration. [H]

- `real` appends `realpath` output; `kind` uses lstat: 1 regular, 2 directory, -1 other, 0 invalid/error/absent. Paths are nonempty, NUL-free, <4096 bytes; relative/dot paths accepted. Read and list use O_NOFOLLOW only on the **final** opened path; ancestor symlinks may be traversed.
- `read` requires regular fstat and initial size <=1 MiB, checks actual reads too, but can append partial output before false, ignores close error, and can inspect a chunk beyond the limit. `list` sorts, stages <=1 MiB counting newline delimiters and <=100000 names, rejects CR/LF names for the entire call, no kind metadata. Its entry limit and byte accounting differ from goose-fs.
- `mkdir` attempts recursive mode-0700 creation and lstat prefix checks. Path-based check/use races remain; this is not equivalent to a held no-follow descriptor walk.
- `write` uses mkstemp sibling + fchmod + fsync + close + link for exclusive publication or rename for replacement; executable mode 0755, otherwise existing regular mode bits or 0600. `write_scratch` skips fsync. No native payload-size guard here; no parent-directory fsync; prechecking destination regularness does not prove race-free final identity. Temp suffix reduces usable path length. Ordinary cleanup attempts unlink but ignores its failure.
- `lock` opens a final-no-follow regular file, 0600 before umask, CLOEXEC, takes nonblocking exclusive flock, returns owned fd or -1; unlock closes it. Contention and other errors collapse. Native resources require explicit lifetime handling.
- Selected copy consumes NUL-delimited relative paths <=1 MiB, <=100000 files, <=64 parent components, cumulative 256 MiB advertised sizes; descriptor-relative descendant traversal rejects links, but initial base opens protect only their final component. Destination files exclusive, modes normalized to 0644/0755, dirs 0700. Tree copy counts entries, caps recursion at depth 64, rejects CR/LF and nonregular/nondirectory entries, skips `.git`, `target`, `.honk`, `.toolchain`, `.build`. Linux copy_file_range has a buffered fallback and exact advertised-length check. Failure can leave partial output; no sync/rollback transaction.
- Recursive remove uses no-follow descendant traversal and depth 80, unlinks final non-directory entries, missing entries succeed; initial parent open has final-only no-follow. Its path grammar rejects direct-root children such as `/name`. `unlink_regular` separately walks all parent components without symlinks, permits relative/dot/dotdot parent syntax, checks regularness then unlinks (no identity guarantee across replacement).
- Executable install streams with a 64 KiB buffer and 256 MiB cap, checks source regularness/final no-follow, publishes sibling temp mode 0755 via link or rename after fsync/close; it lacks parent sync and all-component protection. It limits actual bytes but does not require equality to the initially observed size.

Therefore retain Honk's selected-copy, skip policy, install and scoped locks as **consumer scenarios**, not generic defaults or a universal safety baseline. A general library can supply stronger parent traversal while leaving application ignore lists and package policies outside the filesystem core.

## Fair measurement plan: all four implementations

No competitor measurements were performed for this research. The existing [published benchmark report][FB] compares two goose-fs revisions (`6b8c079...` and `3c863ca...`) on tmpfs, not Rust, Go or Goose stdlib. It cannot support a competitor ranking, disk durability claim or universal performance statement.

Use identical fixtures and operation boundaries for **goose-fs, pinned Goose stdlib, Rust, Go**. Pin binary/source revisions, flags, native compiler/toolchain, OS/kernel/libc, architecture, filesystem/mount options, storage, CPU affinity/load and cache state. Alternate/randomize order; publish raw repetitions, distributions, allocations/peak memory and correctness checks; include regressions and failed/unsupported cases. Separate warm cache, cold-storage and fsync workloads. Do not use machine-wide cache dropping without an appropriate dedicated environment. Optimizations such as kernel-assisted copy must preserve declared semantics and be reported.

Two result groups are mandatory:

1. **Native public APIs.** Measure each API as shipped and attach a policy tuple: platform, bounds, final/intermediate-link handling, regular-only checking, overwrite/create mode, sync level, sort order, kind/metadata work, output encoding/ownership, error behavior. These are task-cost comparisons with differences, not equal-security rankings. Unsupported operations appear as unsupported; don't substitute a different operation.
2. **Matched contract implementations.** Implement adapters with the same descriptor traversal, flags, validation, chunk/bounds checks, sorting/type work, output copies/clearing and sync requirements. Cost of adapters stays inside the measurement. Plain Rust/Go APIs and Goose whole-file wrappers cannot enforce all-component no-follow alone; a Linux OS adapter is necessary. Label it **Rust/Go/Goose + hardened adapter**, not a stdlib guarantee. Report adapter source. For retained-handle microbenchmarks, acquire handles outside timing equally; report separate open/close and end-to-end rows.

| List / incremental iteration | 0/1/100/4096 entries, long/binary/CR/LF names, kind-hint vs full metadata; overflow. | Separate unsorted names-only, bytewise-sorted names-only, owned entries+kind, full-stat rows; identical accounting/limits. No timed printing; render newline protocol separately. Goose's omitted names and Honk's rejected names cannot be scored as equal complete enumeration. |
| Stat / permissions / times / links | File/dir/symlink/missing/denied; follow vs no-follow; handle vs path metadata; mode/time changes; link create/read/unlink. | Same lookup policy and fields, error classification, timestamp precision and platform capabilities. Predicate APIs that hide errors are different workloads. Goose stdlib lacks general metadata/mutation/link APIs. |
| Recursive operations / copy | mkdir_all; empty vs populated remove; file/selected/tree copy; shallow/wide/deep trees, 64 KiB+ files, stable and changing sources. | Same filters, modes, sort order, symlink policy, overwrite, cumulative/depth budgets, source-length policy and cleanup; validate manifest/content hashes. Compare generic copy separately from Honk's application filtering. |
| Temp / locks / adapters | Temp create-close-remove; uncontended acquire-release and multi-process contention; filesystem-interface traversal. | Include randomness/exclusive creation/cleanup; explicit lock mode and lifetime; release before next sample. Pure Goose stdlib unsupported rows remain visible; Go os locking also unsupported without an OS adapter. |

Before publishing performance claims, require independent public-interface correctness oracles for each adapter and hostile-path/failure tests. Claim only measured operation/configuration improvements, with uncertainty; never infer complete feature parity or “outperforms Rust/Go/Goose” from a subset.

## Open decisions before implementation

1. Which platforms are required, and at which milestone? Linux-first delivery is reasonable, but does not meet the references' broader platform coverage. What unsupported-capability/error contract will Windows and other Unix backends use?
2. Keep strict no-follow as the only default, or offer a separately named link-following/root-confined API? Are canonical resolution and link creation in scope now? These policies are different from each other.
3. Which resource ownership model prevents copying/double-close, and what reclaims native handles after contained-worker abort? Defer alone is insufficient.
4. Are metadata mutations/path names required to preserve arbitrary Unix bytes, while virtual filesystem adapters use a separate UTF-8 domain? Which modes/ownership/timestamps need portable coverage?
5. Which atomic-publication durability levels are public, and how is “published but parent sync failed” represented? Must replacement preserve existing mode, use private mode, or accept caller-selected mode?
6. What per-call, total-byte, entry, depth and work budgets serve streams/copies/recursive removal? Does recursive failure return partial progress? Whole-file convenience limits should remain explicit.
7. Which conveniences belong in the core versus composition: tree-copy filters, executable install, canonical paths, shared/blocking locks, raw descriptors? Prefer demonstrable consumer needs without shrinking the primary inventory.
